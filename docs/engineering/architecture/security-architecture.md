### 1. Architectural Security Principles & Boundary Model

Security in AayurFace is enforced across five defense-in-depth layers, eliminating the critical vulnerabilities discovered in Phase 00 (mock `localStorage` auth, wildcard CORS, unauthenticated Edge Functions):

```text
Layer 1: Network & Edge Gateway    ──► Strict CORS Whitelist, IP/User Throttling, TLS 1.3
Layer 2: Identity & Session        ──► Supabase Auth (bcrypt), Asymmetric JWTs, 60m TTL
Layer 3: Application Authorization  ──► Server-Side Identity Derivation (auth.uid()), RBAC
Layer 4: Data Layer Isolation       ──► PostgreSQL Row-Level Security (RLS) on 100% of tables
Layer 5: Biometric Asset Storage   ──► Private Zero-Read Buckets, 15-Minute Signed URLs
```

---

### 2. Authentication & Session Architecture

1. **Elimination of Mock Authentication:** The insecure mock `localStorage` mechanism in `src/contexts/AuthContext.tsx` is completely decommissioned.
2. **Supabase Auth Integration:** User authentication is mediated by Supabase Auth utilizing standard bcrypt/Argon2 password hashing (work factor $\ge 10$) and OAuth 2.0 PKCE for Google social login.
3. **JWT Token Lifecycle:**
   * **Access Tokens:** Short-lived JWTs (validity: 60 minutes) signed asymmetrically via RS256.
   * **Refresh Tokens:** Rotating single-use refresh tokens stored in secure, SameSite cookies or protected memory.
   * **Session Expiry:** Expired tokens automatically trigger background rotation; failure immediately resets client state and redirects to `/auth/login`.

### 3. Database Row-Level Security (RLS) Policies

Every PostgreSQL table containing user or health data must enforce Row-Level Security. Direct queries bypass are strictly forbidden:

```sql
-- Architectural Pattern for RLS Enforcement
ALTER TABLE profiles ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can only view their own profile"
    ON profiles FOR SELECT USING (auth.uid() = user_id);
CREATE POLICY "Users can only update their own profile"
    ON profiles FOR UPDATE USING (auth.uid() = user_id);

ALTER TABLE scan_results ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can only view their own scan snapshots"
    ON scan_results FOR SELECT USING (auth.uid() = user_id);
CREATE POLICY "Users cannot update immutable snapshots"
    ON scan_results FOR UPDATE USING (false);
```

### 4. Biometric Facial Data Protection & Privacy Architecture

Facial imagery constitutes sensitive biometric personal data; the privacy architecture is designed to support applicable data-protection obligations (including principles of the Indian DPDP Act 2023 and GDPR Article 9; formal legal and compliance review is required):
* **Ephemeral RAM Landmarking:** Continuous video stream frames are evaluated exclusively in volatile WebAssembly memory. Raw video frames are NEVER transmitted across networks or written to persistent client storage.
* **Private Storage Bucket (`facial-captures`):** Target architecture requires public access to be blocked at the storage configuration layer.
* **Signed URL Ingestion:** The client uploads the single approved frame using an HMAC-signed S3 URL generated by an authenticated Edge Function with a proposed 15-minute Time-To-Live (TTL) security policy.
* **Purge & Retention Policy (DEC-004):**
  * The architecture supports immediate hard-purging of raw facial frames after feature extraction, retaining only the derived numerical vector (`VisualObservations`).
  * If a user requests account deletion, a cascading database trigger and storage worker permanently purge all biometric assets within 24 hours.

### 5. Threat Mitigation Matrix (OWASP API Security Top 10)

| OWASP API Threat | Potential Risk in AayurFace | Architectural Mitigation & Control |
|---|---|---|
| **API1: Broken Object Level Auth (BOLA / IDOR)** | User A accesses User B's scan result by altering URL UUID. | Server-side identity extraction from JWT (`auth.uid()`); PostgreSQL RLS enforces `auth.uid() = user_id`. Client `userId` parameters are rejected. |
| **API2: Broken Authentication** | Password brute-force or token forgery. | Supabase Auth bcrypt hashing, progressive login delays, rate-limiting on `/auth/v1/token`, asymmetric JWT signatures. |
| **API3: Broken Object Property Level Auth** | User elevates role to `admin` during registration. | Client cannot write to `profiles.role`; role assignments require database service-role execution. |
| **API4: Unrestricted Resource Consumption** | Malicious actor spams `/analyze-multimodal`, exhausting OpenAI quota. | Configurable rate-limiting middleware (DEC-006: 5 runs/hour); request payload size capped at 5MB. |
| **API5: Broken Function Level Auth** | Regular user invokes `/admin-knowledge-ingest`. | Middleware verifies `profiles.role = 'admin'`; non-admin callers receive HTTP 403 Forbidden. |
| **API6: Unrestricted Access to Sensitive Business Flows** | Bot creates synthetic accounts and drains AI inference budget. | Mandatory email verification, CAPTCHA on signup (if abuse detected), rate limits per IP. |
| **API7: Server-Side Request Forgery (SSRF)** | Edge Function fetches malicious internal URLs via storage path. | Storage paths validated against strict regex (`^facial-captures\/[0-9a-f-]{36}\/[0-9a-f-]{36}\.jpg$`). |
| **API8: Security Misconfiguration** | Wildcard CORS `*` allows cross-origin credential theft. | CORS headers restricted to verified production domains (`https://aayurface.app`, `localhost:5173`). |
| **API9: Improper Inventory Management** | Zombie or unauthenticated API versions exposed. | All endpoints versioned under `/api/v1/...`; deprecated versions decommissioned via gateway. |
| **API10: Unsafe Consumption of APIs** | OpenAI generates malicious scripts or ungrounded remedies. | AI outputs validated against Zod contracts; free-text inputs enclosed in strict XML delimiter fences. |
