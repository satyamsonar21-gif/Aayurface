# Phase 13 Architectural Decision Records (ADRs)
**Status:** Approved & Implemented  
**Date:** September 2026  
**Standard:** ISO/IEC/IEEE 42010 Architecture Decisions  

---

## ADR-013: Six-Tier Knowledge Source Authority Model
- **Context:** Classical Ayurvedic knowledge, modern pharmacological studies, internal research, and tabular datasets carry drastically different epistemological validity. Treating all sources as equal creates high risk of generating unverified claims.
- **Decision:** Establish an explicit 6-Tier Authority Hierarchy (Tier 1: Brihat-Trayi Sanskrit Primary; Tier 2: Scholarly Translations/Lexicons; Tier 3: Peer-Reviewed Modern Research; Tier 4: Project Research; Tier 5: Computational Datasets; Tier 6: Unverified/Quarantined).
- **Consequences:** RAG queries filter on authority tiers; citations explicitly display tier metadata; Tier 5/6 sources cannot be cited as classical doctrinal truth.
- **Security/Safety:** Prevents hallucinated or low-quality sources from contaminating user-facing wellness guidance.

## ADR-014: Idempotent Knowledge Ingestion Architecture
- **Context:** Ingesting large corpuses repeatedly risks data duplication, inconsistent chunk versions, and cache pollution.
- **Decision:** Base document and chunk identity on a composite cryptographic hash: `SHA256(sourceId + sourceVersion + contentHash + parserVersion)`.
- **Consequences:** Ingestion is fully idempotent. Re-indexing identical sources creates zero new database rows.
- **Security/Safety:** Guarantees traceability and prevents retrieval noise from duplicate chunks.

## ADR-015: Configurable & Versioned Embedding Strategy
- **Context:** Hardcoding embedding dimensions or providers creates coupling. Embeddings may be generated client-side (small models) or via cloud APIs (e.g., text-embedding-3-small).
- **Decision:** Decouple embedding generation via a provider interface (`EmbeddingProvider`) with explicit runtime versioning (`embeddingModel`, `embeddingVersion`, `dimension`).
- **Consequences:** In-memory deterministic embeddings used for test and offline evaluation; cloud/vector store embeddings used in production with strict version tracking.
- **Security/Safety:** Prevents stale embedding mismatches across model updates.

## ADR-016: Dual Vector Storage Architecture (In-Memory + Supabase pgvector)
- **Context:** The application runs in both local browser/test environments (Vitest/Node/Client) and server/database environments (Supabase PostgreSQL).
- **Decision:** Implement a dual-mode vector store interface. The local environment uses a high-performance in-memory cosine similarity engine with metadata filtering; the server environment leverages PostgreSQL `pgvector` with HNSW indexing.
- **Consequences:** 100% of unit, integration, and adversarial tests execute deterministically without requiring an active external database connection.
- **Security/Safety:** Row-level security (RLS) protects database records, ensuring user audit traces remain private.

## ADR-017: Multi-Stage Hybrid Retrieval & Gating Strategy
- **Context:** Vector search alone can return semantically close but conceptually irrelevant chunks, particularly in dense Ayurvedic domains.
- **Decision:** Implement a pipeline: Query Normalization $\to$ Intent Classification $\to$ Vector Cosine Search ($\ge 0.70$) $\to$ Metadata Filtering (Tier, Language, Status) $\to$ Reranking $\to$ Evidence Gating ($\ge 2$ verified chunks required for high-confidence output).
- **Consequences:** If gating fails, the system executes deterministic safe fallback rather than guessing.
- **Security/Safety:** Drastically reduces hallucinations and enforces the "no-evidence" boundary.

## ADR-018: Strict Claim-to-Evidence Citation Architecture
- **Context:** LLMs frequently invent citations or shlokas when prompted to provide references.
- **Decision:** Citation IDs must originate exclusively from the retrieval system. The generation prompt receives candidate IDs; post-generation validation asserts every cited ID exists in the retrieved set.
- **Consequences:** Any fabricated citation ID immediately causes output rejection.
- **Security/Safety:** Zero tolerance for fabricated classical verses, authors, or page numbers.

## ADR-019: Non-Diagnostic Wellness & Output Safety Boundary
- **Context:** Users may ask medical questions or expect facial analysis to diagnose diseases or constitutional types (Doshas).
- **Decision:** Implement a multi-stage deterministic safety validator that scans for prohibited clinical vocabulary (disease names, prescription drugs) and prevents direct "Face $\to$ Dosha" or "Face $\to$ Prakriti" inferences.
- **Consequences:** Medical diagnosis requests are refused with a safe referral to qualified medical practitioners.
- **Security/Safety:** Ensures full compliance with non-diagnostic wellness standards.

## ADR-020: Evidence-Grounded XAI Without Chain-of-Thought Leakage
- **Context:** Exposing raw model thoughts risks prompt leakage, confusion, and unverified reasoning traces.
- **Decision:** Anchor explainability around structured evidence: observed signals, user context, retrieved sources, agreement/conflict analysis, scientific limitations, and negative boundaries.
- **Consequences:** Users receive clear, verifiable, auditable explanations answering the 7 core explainability questions.
- **Security/Safety:** Eliminates internal prompt disclosure and prevents fabricated "AI logic".

---

## ADR-021: Knowledge Runtime Versioning (`KnowledgeRuntimeVersion`)
- **Context:** As literature, rules, models, and embeddings evolve, previous assessment explanations must remain auditable.
- **Decision:** Bundle full provenance metadata (`knowledgeVersion`, `sourceVersion`, `embeddingVersion`, `retrievalVersion`, `promptVersion`, `modelVersion`) into every RAG response and audit trace.
- **Consequences:** Any past response can be forensically audited against the exact corpus and model state at generation time.
- **Security/Safety:** Full auditability and regulatory compliance.

---

## ADR-022: Dual Prompt Injection Defense (User & Corpus Isolation)
- **Context:** Attackers can inject instructions via user chat prompts or by embedding malicious commands in ingested documents.
- **Decision:** 
  1. Sanitize user inputs by rejecting prompt override keywords and structural escape delimiters.
  2. Treat all retrieved knowledge chunks as passive data by enclosing them in XML `<classical_evidence>` delimiters, with explicit system instruction primacy commanding the model to ignore instructions inside data blocks.
- **Consequences:** Adversarial payloads in either user input or documents cannot hijack system instructions.
- **Security/Safety:** Robust defense against prompt injection, goal hijacking, and system prompt leakage.
